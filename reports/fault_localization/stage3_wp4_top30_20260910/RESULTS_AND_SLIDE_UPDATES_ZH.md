# Code Llama 最多 30 個候選重排：實驗結果與簡報更新

執行日期：2026-09-10（臺灣時間）。本次確實執行本機模型，共完成 46 個案例；不是推估結果。

## 1. 可以直接向教授說明的結論

> 我們另外測試，把原本挑出的候選全部交給 Code Llama，最多 30 個，再請模型重新排序並取前 5 個。在相同的 46 個案例中，固定規則找到答案的有 28 個，模型重排後只有 17 個，命中率由 60.87% 降為 36.96%。因此，這次擴大模型看到的候選範圍，仍沒有改善結果，目前繼續保留固定規則作為後續流程的基準。

這是本輪開發案例的結果，不能擴大解讀成所有模型或所有資料都會退步。回覆完整度比舊實驗好，但定位準確度沒有因此提高。

## 2. 實際成績

前 K 名命中率：每個案例輸出的前 K 個位置，是否至少包含一個評分答案。

| 方法 | 前 1 名 | 前 3 名 | 前 5 名 |
| --- | --- | --- | --- |
| 固定規則 | 12／46＝26.09% | 22／46＝47.83% | 28／46＝60.87% |
| 舊實驗：Code Llama 看前 10 個 | 5／46＝10.87% | 19／46＝41.30% | 27／46＝58.70% |
| 本次：Code Llama 看全部候選，最多 30 個 | 9／46＝19.57% | 15／46＝32.61% | 17／46＝36.96% |

模型欄均包含輸出失敗時回退到固定規則的結果。新舊實驗是同一組 46 個案例，不能加總成 92 個獨立案例。

### 和固定規則相比

- 前 5 名少命中 11 個案例，降低 **23.91 個百分點**。
- 逐案例比較：1 個原本沒命中的案例變成命中，12 個原本命中的案例變成沒命中；其餘 16 個兩者都命中、17 個兩者都沒命中。
- 配對 bootstrap：2,000 次重抽樣、種子 42。前 5 名差值的 95% 信賴區間為 **−36.96 至 −10.87 個百分點**，整段低於 0；這批案例有支持模型排序較差的證據。
- 前 1 名差值的區間包含 0，不應將所有指標都描述為已證明退步。前 3 名差值區間為 −26.09 至 −4.35 個百分點。

### 和舊版模型相比

前 5 名從 27 個命中降到 17 個，降低 21.74 個百分點。但本次同時調整候選數與模型長度設定，不能把全部變化只歸因於「候選變多」。

### 候選召回率是否改變？

**仍為 68.64%。** 本次直接沿用既有候選清單，沒有重跑候選挑選，也沒有增加新的程式位置；只是改變模型可以排序的範圍。這個數字是既有候選實驗的每案例召回率平均，不是本次模型的前 5 名命中率。

## 3. 輸出是否完整、花了多久？

- 有效排序：**44／46＝95.65%**。
- 回退固定規則：**2／46＝4.35%**。本輪達到既定有效率至少 95%、回退率至多 5% 的數值門檻，但不代表定位品質達標或通過完整研究驗收。
- `matplotlib__matplotlib-26341`：回覆達到 3,072 token 上限，`done_reason=length`，排序不完整。
- `sympy__sympy-24909`：回覆重複列出 C3、漏掉 C2，即使回覆正常結束仍未通過完整性檢查。
- 每案例平均約 **25.12 秒**，中位數 22.98 秒，p95 約 **40.55 秒**，最慢 49.73 秒；46 次請求合計約 **19.26 分鐘**。這是模型請求的實測時間（包含請求與必要的載入時間），不是整套定位、補丁與測試流程的時間，也沒有和固定規則做完整延遲配對比較。

## 4. 本次到底怎麼跑？

```text
沿用固定規則已保存的候選清單（最多 30 個）
→ 將全部候選打亂順序，隱藏原排名與分數
→ 提供錯誤描述與候選程式片段
→ Code Llama 對每個候選給分與理由
→ 檢查是否漏列、重複或分數不合法
→ 有效時取新排序前 5 個；失敗時改用固定規則前 5 個
→ 與同一份評分答案比對
```

模型為本機 Ollama 的 `codellama:7b-instruct`（7B、Q4_0），沒有微調。模型 digest 已保存在 manifest；評分答案沒有加入模型請求。

| 設定 | 本次值 |
| --- | --- |
| 最大候選數／最終結果數 | 30／5 |
| 實際候選數 | 45 個案例各 30 個；`scikit-learn__scikit-learn-13087` 原清單只有 23 個，全部使用 |
| 候選洗牌種子 | 20260908（不是模型生成 seed） |
| temperature／top_p | 0.0／1.0 |
| num_ctx／num_predict | 16384／3072 |
| 單次請求 timeout | 600 秒，沒有案例達到這個上限 |
| 錯誤描述／每候選程式片段上限 | 4000／1200 字元，沿用原 pilot |

舊版 `num_predict` 是 768，沒有明確傳入 `num_ctx`，timeout 是 180 秒。本次擴大可讀取與回覆長度，以支援更多候選；這是新設定下的探索性實驗，不是只改候選數的嚴格單變因比較。

此次新增獨立的執行與分析腳本，沒有把整合主程式的模型路徑改成正式預設。

## 6. 報告時要保留的限制

這次仍是相同的 46 個開發案例，沒有新增獨立測試資料。它們都符合前一階段至少找到一個正確檔案的條件，不能將 36.96% 當成整套系統的端到端成功率。

模型看到的是每個位置最多 1200 字元的片段，不是完整函式或全部檔案。共有 18 個 `<module>` 候選的程式片段為空，仍提供名稱、檔案與位置等資料；這是沿用既有資料載入方式的限制，尚未證明它造成多少錯誤。

實際記錄的輸入 token 加輸出 token 最大值是 15,413，低於本次 16,384 的設定容量；這項數值檢查不能替代對模型注意力或完整理解程度的驗證。
