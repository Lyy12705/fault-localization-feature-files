## 2. 簡報建議順序

以下每一小節可作為一頁簡報，順序是「問題 → 動機 → 方法 → 流程 → 結果 → 限制 → 下一階段」。

### 第 1 頁：為什麼需要第三階段？

前一階段找到可能有問題的檔案，但一個檔案裡可能有很多函式。第三階段要進一步指出：應該優先檢查哪個函式、方法或類別？

- 輸入：錯誤描述，以及前一階段選出的 5 個候選檔案。
- 處理：讀取程式結構，從中選出並排序可能出錯的位置。
- 輸出：前 30 個候選、前 5 個定位結果，以及成功或失敗的診斷資訊。

本輪實驗固定使用已保存的 E7-A 檔案定位結果，讓不同方法都從同一份 Top-5 檔案開始比較。不能描述成重新跑完完整 E8-A 系統。

口頭說法：

> 我們把「找對檔案」再往下縮小成「找對函式」。先檢查答案有沒有進入候選，再檢查答案能不能排到前面。

### 第 2 頁：先讓系統分清楚每個函式

**問題與目的：** 不同檔案可能都有 `login()`，類別裡也可能有同名方法。只比名稱容易認錯，所以要記錄完整位置與版本。

**實作方法：** 使用 AST，也就是把程式碼解析成結構，找出函式、類別與它們的包含關係。`extract_symbols_from_source()` 負責解析，`SymbolRecordV1` 保存完整名稱、種類、行列位置及來源。

`make_stable_symbol_id()` 根據 repository、base commit、檔案路徑、程式語言、種類、完整名稱及行列範圍，產生 SHA-256 ID。同一版本、同一位置重複解析會得到相同 ID；版本或位置改變，ID 也可能改變。

**輸入 → 輸出：** 修補前版本的原始碼 → 有名稱、位置、來源與 ID 的程式單位清單。

**完成成果：** 已能區分正常解析、語法錯誤、缺檔、不支援語言，以及合法但沒有函式等情況。

**限制：** 解析出程式結構，不代表已理解錯誤根因；後面仍需要排序。正式 Symbol 定位實驗也不能直接推廣為所有語言均有相同 AST 支援。

### 第 3 頁：如何建立評分用的正確答案？

**問題與目的：** 原本只有「哪個檔案被修改」的答案，不足以評估函式定位，所以要找出修補涉及哪些程式單位。

實作流程：

1. `parse_unified_diff()` 讀取開發者的修補差異。
2. `map_patch_hunks_to_symbol_gold()` 將修改或刪除行對應到修補前版本中最內層的函式或方法。
3. 只有新增行時，以插入位置附近的原始位置作為依據；函式外的修改歸入 `<module>`，即模組層級。
4. 新增檔案、來源缺失或無法明確對應的情況，記錄排除原因。
5. 保存來源證據，抽樣檢查對應是否正確。

**輸入 → 輸出：** 開發者修補紀錄＋修補前程式结构 → Gold（評分答案）、稽核表與來源證據。

| 項目 | 數據 |
|---|---:|
| 開發用問題案例 | 61 筆 |
| 專案來源 | 12 個 repositories |
| 可讀取的修補前版本 | 61／61 |
| Gold 紀錄 | 207 筆：205 筆成功對應、2 筆排除 |
| 抽樣檢查 | 50 筆 |
| 位置對應正確／來源完整 | 50／50、50／50 |

**限制：** 207 筆是答案紀錄，不是 207 個獨立問題。50 筆檢查由 Codex 對照來源完成；若正式研究要求外部人類審查，仍要補做。修補位置是評估依據，不代表已證明每個位置都是唯一根因。

### 第 4 頁：不用 LLM，怎麼找出可疑函式？

**動機與目的：** 先建立可重複執行的基本方法，才能判斷加入 LLM 是否有幫助。這個基本方法稱為 deterministic baseline，白話就是「依固定規則計分與排序的比較基準」。

`rank_symbol_candidates()` 提供兩種方法：

| 方法 | 白話說明 |
|---|---|
| B0：TF-IDF | 比較錯誤描述和程式搜尋文字中，重要詞彙是否相近。 |
| B1：多種線索加權 | 除了文字相似度，也考慮識別字、錯誤堆疊、函式名稱，以及前一階段的檔案分數。 |

B1 的固定權重：

```text
總分 = 50% × 文字相似度
     + 20% × 識別字線索
     + 15% × 錯誤堆疊線索
     + 10% × 程式單位名稱線索
     +  5% × 正規化後的檔案分數
```

這些是程式設定的規則權重，沒有用 Gold 訓練出一個新模型。

選定的 `coverage-aware-v1` 意思是「挑候選時兼顧不同位置的覆蓋」。`_select_coverage_aware_symbols()` 保留高分候選，為各檔案保留模組層級候選，再從已有線索的類別補入成員，最多配置 5 個類別成員擴展名額，最後去重並補滿 30 個。

**輸入 → 輸出：** 錯誤描述＋5 個候選檔案的程式單位＋檔案分數 → 30 個候選與前 5 名結果。

**限制：** 只有 30 個名額，加入新候選可能擠掉原本的正確答案；目前規則在其他資料上的效果仍需驗證。

### 第 5 頁：如何評分，才不會混淆結果？

```text
錯誤描述＋固定的 5 個候選檔案
→ 取得程式單位清單
→ 固定規則選出前 30 個
→ 直接取前 5 個，或讓 LLM 重排部分候選
→ 用 Gold 檢查結果
```

評估器優先比對可信的 Symbol ID；否則比對「檔案路徑＋種類＋完整名稱」。只比名稱尾端等寬鬆比對，僅供診斷。

| 指標 | 白話意思 |
|---|---|
| Candidate Recall@30 | 每題應找到的程式位置，有多少比例進入前 30 個，再對所有題目取平均。 |
| Exact Hit@5 | 前 5 名中，是否至少有一個位置符合答案。 |
| Conditional（有條件評估） | 只看前一階段至少找到一個正確檔案的題目。 |
| End-to-end（完整流程評估） | 保留整批題目，包括前一階段找錯檔案的題目。 |

本輪 61 題中，46 題符合 conditional 條件。後面的 LLM pilot 是這 46 題的結果，不能當作完整流程成功率。

### 第 6 頁：候選方法有改善，但仍未達標

以下是同一組資料、46 題有條件評估的 Candidate Recall@30。

| 方法 | 找回率 | 判讀 |
|---|---:|---|
| B0：TF-IDF | 60.60% | 最基本的比較方法 |
| B1：多線索加權 | 64.36% | 比 B0 好 |
| 每檔初始名額限制 4／6／8 | 61.34%／53.35%／56.24% | 未優於 B1 |
| 保留模組層級候選 | 64.94% | 小幅改善 |
| coverage-aware-v1 | **68.64%** | 本輪選定方法 |

相較 B0 提升 8.04 個百分點，相較 B1 提升 4.28 個百分點；距離原定 90% 門檻仍差 21.36 個百分點。

為什麼還沒達標？完整候選池內的答案找回上限為 90.41%，但挑出前 30 個後只剩 68.64%。90.41% 是用答案計算的診斷上限，並非實際排序成績。

這 46 題共有 137 個去重後的答案位置：

| 情況 | 數量 |
|---|---:|
| 已進入前 30 個 | 88 |
| 候選池裡有，但沒有排進前 30 個 | 30 |
| 所在檔案沒有進入前一階段的前 5 名 | 17 |
| 候選識別資訊與答案不一致 | 2 |

主要問題是「池內有答案，但選候選時漏掉」。68.64% 是逐題算比例後平均，不能直接用 88／137 代替。

### 第 7 頁：做過哪些改善？為什麼沒有採用？

共同目的都是找回漏掉的答案；輸入為原候選、分數與程式結構，輸出仍只有 30 個名額。

| 改善方法 | 實際做法 | Recall@30 | 相對 coverage-aware-v1 |
|---|---|---:|---|
| 找附近的定義 | 最多 5 個擴展名額，找同檔、互不重疊、距離不超過 100 行的定義。 | 64.70% | 找回 1 個，失去 7 個 |
| 呼叫關係 v1 | 從候選程式片段重建呼叫關係，找一層呼叫者或被呼叫者。 | 66.02% | 找回 2 個，失去 6 個 |
| 呼叫關係 v2 | 改用完整索引的 `CodeIndex.call_graph`，再將兩端限制在本次候選範圍。 | 68.20% | 找回 4 個，失去 5 個 |

v1 有 22 個案例看不到呼叫關係。檢查發現原始定義全部存在，其中 20 個在完整索引裡已有連到其他池內候選的關係：15 個涉及同檔重建時遺失資訊，5 個涉及跨檔 import 解析資訊遺失。

v2 修正這個問題，結果從 66.02% 提升到 68.20%，但仍低於選定基準的 68.64%。這表示「修好呼叫圖資訊」不一定就能提高固定 30 個名額下的整體找回率。

**目前決策：** 三次改善都沒有超過基準，因此本輪停止相近規則的微調。換用語意候選等方向屬未來研究，尚未完成驗證。

### 第 8 頁：為什麼測試 Code Llama？怎麼使用？

**動機與目的：** 固定規則主要看文字和結構線索，因此想測試程式碼模型是否能根據錯誤描述與程式內容，把真正有問題的位置排得更前面。Reranking 就是「將已有候選重新排序」。

本輪使用現成的 `codellama:7b-instruct`，透過本機 Ollama 做推論，沒有重新訓練或微調。

獨立 pilot 腳本的流程：

1. 沿用 coverage-aware-v1 已保存的 30 個候選。
2. 取前 10 個，打亂順序並重新標成 C1～C10，避免透露原排名。
3. 給模型錯誤描述、候選名稱、檔案、行號與程式片段，不提供原排序分數。
4. 一次請求要求每個候選回傳 ID、0～1 分數與理由，依結果選前 5 個。
5. 缺漏、重複、未知 ID、非有限數值或超界分數等不合法結果，整題回退到原本固定規則的順序。

| 設定 | 實際值 |
|---|---|
| 模型 | codellama:7b-instruct |
| 模型看到的候選／最後輸出 | 10／5 |
| temperature／top_p／num_predict | 0.0／1.0／768 |
| 請求逾時上限 | 180 秒 |
| 候選洗牌種子 | 20260908 |

洗牌種子控制候選順序；目前 client 沒有把它傳成模型的生成種子。

**輸入 → 輸出：** 錯誤描述＋候選程式片段 → 模型排序的前 5 個，或失敗後回退的結果。

**限制：** 模型只看前 10 個，無法找回不在這 10 個之內的答案。舊主程式仍有每批 5 個再合併分數的雛形，本輪結果來自獨立 Top-10 腳本，不能說所有入口都已改成相同方式。

### 第 9 頁：Code Llama 有沒有比較好？

已完成 1 題、10 題的小規模運作檢查，以及 46 題初步比較。以下 LLM 結果包含 4 題失敗後回退原排序的案例。

| 指標 | 固定規則 | Code Llama＋回退 | 差異 | 差異的 95% 信賴區間 |
|---|---:|---:|---:|---|
| 前 1 名至少命中一個答案 | 26.09% | 10.87% | −15.22 個百分點 | [−28.26, −2.17] |
| 前 3 名至少命中一個答案 | 47.83% | 41.30% | −6.52 個百分點 | [−21.74, +8.70] |
| 前 5 名至少命中一個答案 | 60.87% | 58.70% | −2.17 個百分點 | [−15.22, +10.87] |

信賴區間使用逐題配對資料，固定種子 42、重抽樣 2,000 次計算；表中區間單位也是百分點。

- 前 1 名的差異區間全部小於 0，支持本輪模型排序較差。
- 前 3 名及前 5 名雖然分數較低，但差異區間包含 0，不宜宣稱已證明顯著退步。
- 前 5 名有 4 題改善、5 題退步，沒有淨改善。
- 合法輸出 42／46＝91.30%；回退 4／46＝8.70%，未達至少 95% 合法、最多 5% 回退的門檻。

**本輪決策：不採用 Code Llama Symbol 重排。** 可說「這個模型在目前 46 題與候選設計下沒有帶來改善」，不能擴大成「所有 LLM 都不適合錯誤定位」。

68.64% 是候選找回率，60.87% 是逐題前 5 名命中率，兩者不能直接當成同一種準確率，也不能把前者當作後者的數值上限。

## 3. 教授可能會問：模型是不是事先知道答案？

**提供真實程式碼，不等於提供正確答案。** 關鍵在於提供的是修補前的程式，還是已經附帶修補結果與答案標記。

### 本輪模型看到什麼？

| 模型會看到 | 模型 prompt 沒有提供 |
|---|---|
| 錯誤描述 | Gold 答案標籤 |
| 修補前的候選程式片段 | 開發者修補 diff |
| 檔案路徑、函式名稱及行號 | 哪個候選一定是正確答案 |
| 打亂順序後的候選 ID | 原檢索分數及原排名 |

候選是前一階段檢索與第三階段規則排序的結果，不是直接把 Gold 指定的正確函式交給模型。`build_prompt()` 組裝模型輸入；Gold 則供評分與案例資格判斷使用。

### 需要誠實說明的三件事

1. **本輪沒有訓練模型。** 使用現成 Code Llama 推論，沒有用答案更新模型參數。不過，研究者確實使用開發資料的結果選擇候選方法，這屬方法開發，不能當成完全獨立的最終測試。
2. **評估程式知道答案，而且答案有參與選題。** 46 題 pilot 只保留上游至少找到一個正確檔案的案例；這個篩選需要 Gold。因此結果只能說明「上游已找到至少一個正確檔案時」的排序表現。這不等於把答案放進 prompt，但也不是整批案例的端到端驗證。
3. **不能保證模型預訓練完全沒見過相關公開資料。** 目前沒有足夠證據排除預訓練資料重疊，不能宣稱所有資料污染風險已被排除。

可直接回答教授：

> 老師，我們目前沒有用這些資料重新訓練 Code Llama，而是讓現成模型閱讀修補前的候選程式碼，再判斷可能出錯的位置。開發者的修補紀錄是用來建立評分答案，沒有放進模型提示中。不過，這輪 46 題有利用答案篩出前一階段已找到正確檔案的案例，所以是有條件的初步排序實驗，還不能代表整套系統的最終表現。另外，模型預訓練是否見過相關公開資料，目前也無法完全排除。
